# Child records inherit Organization scope transitively through their parent

ADR-0001 and ADR-0024 say every domain concept carries its Organization scope and all schema is Organization-scoped from day one. Child records — `identity_tokens`, `enrollments`, `authorization_codes`, `refresh_tokens`, `client_secrets`, `redirect_uris` — carry no literal `organization_id` column; they are Organization-scoped through an unbroken foreign-key chain to an Organization-scoped parent (`identities`, `applications`, `sessions`). Every lookup that crosses an Organization boundary joins through that parent, and the parent's mandatory `organization_id` is what makes Instance-global identity structurally impossible.

The duplicate-column alternative was rejected: a copied `organization_id` is redundant state that can drift from the parent's, and every write path would need to keep the copy honest. The foreign key is the single source of truth; scope is derived, never restated. Nor do child records use opaque globally-unique identifiers without a scoping parent — that would make cross-Organization reads possible by construction and leave audit attribution unscoped.

Consequences: a new child table must reference an Organization-scoped parent (directly or transitively) and must never float free of one; cross-Organization isolation is a property of query discipline, enforced today by the parent join and by the Management API passing exactly one `organizationId` per lookup. Should a future hosted mode require direct partition-by-Organization or row-level policies, that migration adds and backfills the column then — the ADR is revisited rather than pre-emptively denormalized.
