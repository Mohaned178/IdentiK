# External Identities are federated credentials

An External Identity — a (provider, subject ID) pair from an external provider — attaches to an Identity as an authentication method, exactly like a password. Resolution order at social sign-in: first by (provider, subject ID) — a returning provider user resolves directly; then by email within the Organization — if the provider attests the email as verified, the External Identity attaches to the existing Identity (no separate linking step); otherwise a new Identity is created whose email counts as verified because a trusted provider attested it. Provider attestation is accepted only from providers the deployment marks trusted — configuration owned by the Instance Operator (ADR-0022), not per-request judgment. A different-email social identity never auto-links: email lookup misses, a second Identity is created, and the person merges later by connecting the provider while authenticated (the credential attaches by subject ID, not email). Disconnect is blocked while it would leave an Identity with zero authentication methods. Terminology: toward client Applications we are the OpenID Provider; toward Google we are a Relying Party — one phrase, two relationships; conflating them is how social-login models go wrong. Deferred from MVP; the model is settled so it arrives additively (ADR-0023).
