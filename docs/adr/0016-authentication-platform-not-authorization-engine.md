# Authentication platform, not an authorization engine

The platform's assertions stop at *who the person is* (identity, email, verification state, Enrollment). Application roles — "admin of Zotac" — are the client Application's domain data: stored there, decided there, enforced there. The platform offers no Application-role storage, no permission engine, no policy language for client Applications. What the platform does own is platform-internal authorization: two Administrator Roles — Owner (everything, including destructive settings: secret revocation, redirect URI changes, Application deletion) and Member (day-to-day administration: users, suspensions, Sessions) — deliberately coarse for now. One-line boundary: *we authenticate and assert; you authorize.* This is a positioning statement, not a missing feature — it keeps every client's business rules evolving at the client's speed, and deferring Application-role storage is reversible (attach to Enrollment later) while building it would drag every client's semantics into our token contract irreversibly. Unqualified "Role" is banned vocabulary: it is either an Administrator Role (ours) or an application role (theirs).
