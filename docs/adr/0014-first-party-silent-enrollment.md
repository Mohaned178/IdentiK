# First-party silent enrollment; consent deferred

No Allow/Deny consent screen exists in this release, because consent exists in OAuth to protect a resource owner's data from a third party — and in our model every Application is a first-party arm of the Organization that owns the Identities; both sides of the would-be boundary belong to the same trust domain. Enrollment is silent at first authentication. Scopes exist as integration configuration — the standard OIDC set (openid, email, profile) governing what goes in tokens, requested by the Application, configured by Administrators — not user-granted permissions. The End-User "connected Applications" view is informational; un-enrollment is an Administrator action. Consent is a documented deferred concept, arriving only if third-party Applications ever exist (e.g., a hosted mode); the guardrail is that Enrollment records are shaped so a consent decision can attach later without migration. Rejected: per-app consent screens (friction guarding a boundary we deliberately dissolved); third-party scopes now (an authorization marketplace for a market we don't have).
