# Application structure and client types; public clients never hold secrets

An Application is one integration surface with one client configuration; environments (dev/staging/prod) are deferred, protected by a load-bearing invariant: Enrollment and consent attach to the Application, never to its credentials or redirect configuration — so an Environment concept can be added later without breaking anything. Two first-class types exist: Web Application (confidential client — a backend that holds a Client Secret) and SPA/Mobile Application (public client — PKCE does the secret's job; a Client Secret is never issued to a public client under any circumstance, not at registration, not later, not "temporarily"). The type tells the platform which flows to permit, which screens to render, and which attacks to defend against; a confidentiality toggle would invite misconfiguration. Rejected: three types with machine-to-machine now (authorization without end-user authentication is a different promise — deferred, not silently dropped); a single generic type with a toggle. Accepted cost: dev/staging/prod share one Client Secret for confidential clients, mitigated by multi-secret rotation (ADR-0010).
