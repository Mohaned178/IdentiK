# Client credential and redirect-URI security rules

The Client ID is public and permanent — it appears in URLs, logs, and consent surfaces, and is never rotated (it was never a secret). The Client Secret is stored in verifiable form only (not even Administrators can read it back), displayed exactly once at generation, and supports multiple concurrent labeled, timestamped secrets with individual revocation — making rotation zero-downtime (generate a second secret, redeploy at leisure, revoke the leaked one) and compromise response a routine operation instead of an emergency. Redirect URIs are matched exactly on scheme + host + port + path; no wildcards, no prefixes, ever; HTTPS required with a single carve-out of plain HTTP for loopback (local development). Redirect-URI changes are Owner-governed Organization actions, and every change is recorded as a first-class security audit event in the same surface as suspensions and secret rotations — a silent redirect-URI addition is a code-interception primitive, and "who added that URI, when" must always be answerable. Rejected: prefix/wildcard matching (every relaxation in OAuth's history became a CVE); viewable secrets (every admin compromise becomes every-application compromise).
