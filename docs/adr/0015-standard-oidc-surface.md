# Standard OIDC surface; platform-only token audience

The platform speaks standard OIDC end to end: access tokens are self-contained signed JWTs verifiable offline via a published JWKS endpoint; discovery metadata self-describes the endpoints; authorization, token, userinfo, revocation, and introspection endpoints all behave to spec — so any off-the-shelf OIDC library integrates a client Application with zero proprietary SDK for the core flow, and a self-hoster's IdP outage degrades token *issuance*, not every running Application's request path. ID tokens carry the identity assertion (who, when, email + verification state, for which Application). Load-bearing sub-ruling: **the access token's audience is the platform's own endpoints (userinfo, later management surfaces), never a client Application's resources.** We are an identity provider, not a resource server for client business data; Zotac authorizing Mohamed to see Zotac's orders is Zotac's system talking to itself. Rejected: opaque tokens + mandatory introspection (every request path depends on the IdP being up, no library interop); proprietary token format + SDK (lock-in; not a real Identity Provider).
